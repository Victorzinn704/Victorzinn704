# Fluxo de contribuição

Mantenha cada mudança pequena, rastreável e com validação proporcional ao projeto. Este fluxo complementa as instruções e os testes já existentes no repositório.

1. Abra uma issue com o problema, o resultado esperado e critérios de aceite. Não inclua senhas, tokens, arquivos `.env` ou dados pessoais reais.
2. Confirme o repositório, a branch e as alterações locais com `git remote -v`, `git branch --show-current` e `git status`. Preserve trabalho local ainda não publicado.
3. Atualize a branch padrão antes de começar: `git fetch origin`, `git switch main` e `git pull --ff-only origin main`. Use o nome real da branch padrão quando não for `main`. Se houver divergência, examine o histórico antes de integrar as mudanças.
4. Crie uma branch curta: `git switch -c fix/123-corrige-validacao`. Use `tipo/numero-descricao` para novas tarefas. Prefixos aceitos: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`, `migration`, `hotfix` e `codex`. O número na branch é recomendado, não obrigatório; nomes existentes como `migration/java-2.0` continuam válidos. Uma branch legada fora desses prefixos exige adaptação explícita da regra no projeto, sem reescrever seu histórico.
5. Revise `git diff`, adicione apenas os arquivos da mudança e confira `git diff --cached`. Faça commits por intenção, com descrição em português: `fix(api): rejeita CPF inválido`. O formato é `tipo(escopo opcional): descrição`; use `!` antes de `:` para mudança incompatível. Tipos de commit e título de PR: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore` e `revert`.
6. Execute as verificações documentadas pelo projeto e registre o que realmente rodou. Publique com `git push -u origin fix/123-corrige-validacao`; nos próximos commits, use `git push`. Para atualizar uma branch de trabalho já publicada, use `git fetch origin` e `git pull --ff-only` quando possível; se precisar integrar a base, revise as diferenças e faça merge da branch padrão, resolvendo os conflitos e repetindo os checks afetados.
7. Abra um PR com título no mesmo formato dos commits, motivo, validação e uma linha `Closes #123`, `Fixes #123` ou `Resolves #123`. Também vale a URL completa de uma issue deste mesmo repositório. Vínculos em comentários HTML ou blocos de código não contam. O fechamento automático ocorre quando o PR é integrado à branch padrão.
8. Espere os checks obrigatórios e resolva os comentários. Em projetos individuais, um PR pode ter zero aprovações exigidas; em equipe, siga a revisão configurada. Integre por squash quando esse for o método do projeto, revisando a mensagem final. Preserve os métodos existentes em forks e branches duradouras quando forem necessários à sincronização.
9. Após a integração confirmada, exclua a branch remota pelo PR. Atualize a branch padrão com `git fetch --prune origin`, `git switch main` e `git pull --ff-only origin main` (ajuste `main` se necessário). Para a branch local, use `git branch -d nome-da-branch` apenas se o Git confirmar a integração; após squash ele pode recusar, e nesse caso mantenha a branch até revisar o conteúdo.

Não use push forçado, reset destrutivo ou exclusão de branches com trabalho não integrado para cumprir este fluxo. Não reescreva commits já publicados para padronizar histórico antigo.

O check **PR governance** valida somente título, prefixo da branch e formato do vínculo com issue; ele não consulta se a issue existe e não substitui build, testes, lint, análise de segurança ou revisão. PRs dos autores exatos `dependabot[bot]` e `renovate[bot]`, identificados como bots e em suas respectivas branches `dependabot/` e `renovate/`, são dispensados dessas três regras. Cursos guiados e forks podem manter políticas específicas para preservar exercícios e sincronização.
